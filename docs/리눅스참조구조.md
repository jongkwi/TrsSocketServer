### 1.4 onmw에서 가져오지 말아야 할 결함 **[확인]**
1. STX/ETX 잔여 버퍼가 소켓 스레드 지역변수라 **클라이언트 간 공유** → 세션 구조체 안으로 이동 (Trs의 `m_Rdata` 방식이 맞음)
2. 워커 배열을 `Malloc`으로 만들어 **생성자 미실행** → `new[]`
3. 포그라운드 모드에서 시그널 미등록(SIGPIPE 미처리) → 항상 등록
4. 설정 경로 버퍼 51바이트 → 256
5. `-n` 옵션 `strcmp` 반전
6. `select` fd 1024 제한(FD_SETSIZE 재정의 무효) → **onlic 은 `poll()` 로 구현**(2026-10-14 최종 검증 S2: 190.7 에서 스캐너 세션 누적이 확인되어 제한 제거)
7. Makefile `rm -f *.*`가 linux 폴더 파일 삭제 → 산출물 폴더 분리
8. (앱) 스레드 수를 DB에서 읽음 → Trs는 ini로

## 3. 스레드·DB 핸들 설계 **[제안]**

현재 Windows 버전은 단일 UI 스레드가 소켓 이벤트·타이머·DB를 직렬 처리한다. onmw 패턴을 적용하되, **6321 응답 5초 제한**과 **이벤트 처리 순서 보장**을 유지하도록 워커를 최소화한다.

| 스레드 | 수 | 역할 | DB 핸들 | onmw 대응 |
|---|---|---|---|---|
| main | 1 | 기동·시그널·`while(running)` | `m_pSysDB` (기동 시 `cc_update_time` 초기화, 제외시간 로드) | main |
| LicSocket | 1 | 6321 accept/recv/프레이밍 → `LicRecvWait` 큐 | - | RunAgtSocketThread |
| AlarmSocket | 1 | 6770 accept/recv/heartbeat 응답, 세션 리스트 유지 | - | 동일 |
| EventUdp | 1 | 5363 recvfrom/프레이밍 → `EventRecvWait` 큐 | - | RunUserCTDSocketThread |
| LicRecvWait 워커 | 1 | `IPCS_LOG` INSERT + `lic_access_list` SELECT → `Run`/`Close` 송신 | `LicDB` (ipcs_log DSN) | RecvAgtWaitStack |
| EventRecvWait 워커 | **1** (순서 보장·DB 상태 일관성) | nType 처리, DB 갱신, 6770 푸시, HTTP 큐 적재, 알림톡 INSERT, ACK `Sendto` | `EventDB`(ipcs_log), `AtalkDB`(onpia_check), `SmsDB`(onpia_sms) | RecvIvrWaitStack |
| HttpWait 워커 | 1 | 웹푸시·메일 libcurl POST | - | WaitStack + AlramWeb 역할 |
| Timer | 1 (CTimerObject 내부) | LINK_TIMER 5초: `OnCheckLinkData` | `TimerDB`(ipcs_log), `TimerAtalkDB` | MwTimer |
| Log | CLogObject 내부 ×4 | 파일 기록 | - | LogObject |

- 워커를 1개로 두는 이유: 현재 동작이 직렬이며 `m_pSmsSiteUsers` 공유 버퍼·`CallCenter_Link` 상태 갱신이 순서에 의존한다. 2개 이상으로 늘리면 `szIP % N` 핀 고정이 필요하다(onmw `chdev % n` 방식).
- 6321 워커를 이벤트 워커와 분리하는 이유: 이벤트 처리(HTTP 큐 적재·알림톡 INSERT 다수)가 밀려도 라이선스 응답 5초를 지키기 위함.
- DB 핸들은 onmw 원칙대로 **스레드당 전용**. 총 7개(Sys, Lic, Event×3, Timer×2). PostgreSQL이므로 모두 psqlODBC DSN.

## 8. 서버 2대 구성 **[사용자 결정 2026-10-13: 각 서버에 로컬 DB 설치, 로컬만 바라봄. 이중화는 추후]**

### 8.1 구성

| | 서버 A = `lic.onpia.co.kr` (현 190.44 역할) | 서버 B = `lic2.onpia.co.kr` (현 190.7 역할) |
|---|---|---|
| 앱 | `onlic` `[ROLE] LICENSE=1 ALARM=0 LINK_CHECK=0` | `onlic` `[ROLE] LICENSE=1 ALARM=1 LINK_CHECK=1` |
| 로컬 PG | **통합 스키마**(DB스키마 §6 전체 테이블) | **통합 스키마**(동일 DDL) |
| 초기 데이터 | 44의 `lic_access_list`·`IPCS_LOG`·`nasa_lic*` | 44의 `lic_access_list` **복사** + 7의 `CallCenter_Link`·`SITE_*`·OnAlarm 테이블·`IPCS_LOG` |
| DSN | `ipcs_log`→localhost PG, `onpia_check`→159.134:39999, `onpia_sms`→localhost PG(SMS Agent 설치 시) | 동일 |
| 외부 도구 | NcLicense.exe·IP 등록 도구 → A의 PG | OnAlarm 웹·SMS Agent → B의 PG |

- 두 서버의 DB는 **서로 독립**(현재 운영과 같은 토폴로지). 다른 점은 B에도 `lic_access_list`가 있어 **2차 폴백이 실제로 동작**하고, A에도 알람 테이블이 있지만 `[ROLE]`로 꺼 둔다는 것
- 스키마를 양쪽 동일하게 두는 이유: 추후 이중화(§8.4) 전환 시 DDL 변경 없이 복제만 추가하면 되기 때문

### 8.2 반드시 지켜야 할 것
1. **`ALARM`·`LINK_CHECK`는 B만 1.** A에서도 켜면 A는 UDP를 받지 못하므로 5초 타이머가 전 사이트를 21분 뒤 링크 장애로 판정해 알림톡을 쏟아냄
2. **`lic_access_list`는 두 서버에 같은 내용**이어야 함. 신규 사이트 IP를 A에만 넣으면 A 장애 시 B가 `Close`를 돌려줌(현재 7의 결함 재발). 동기화 방법은 §8.3
3. `IPCS_LOG`는 서버별로 따로 쌓여도 됨(접속 로그). 조회 시 두 서버를 합쳐 보면 됨
4. `CallCenter_Link`·`SITE_*`는 B만 갱신. A의 사본은 사용하지 않음(초기 복사만)

### 8.3 `lic_access_list` 동기화 — **결정(2026-10-13): 지금은 하지 않음, 추후 DB 이중화 때 해결**

B는 초기 복사본으로 판정하고 이후 갱신 없음. 전환 전까지 운영 절차로 B에도 수동 등록 권고. 아래는 추후 선택지 기록.


| 방식 | 내용 | 비고 |
|---|---|---|
| (가) 수동 2회 등록 | IP 등록 도구가 A·B 양쪽에 INSERT | 도구 수정 필요, 누락 위험 |
| (나) cron 복사 (**권고, 단순**) | A에서 주기적으로 `psql -c "\copy lic_access_list to ..."` → B에서 TRUNCATE + `\copy` (예: 5분) | 스크립트 1개, 복제 설정 없음. A 장애 시 마지막 복사본으로 B가 판정 |
| (다) PG 논리 복제 | A `CREATE PUBLICATION` (`lic_access_list`만) → B `CREATE SUBSCRIPTION` | 실시간, 테이블 단위라 가벼움. B 쪽 테이블에 직접 쓰면 충돌 |

### 8.4 추후 이중화로 가는 길 (지금은 미적용)
- 스키마가 동일하므로 B의 PG를 A의 hot standby로 바꾸거나(스트리밍 복제) keepalived VIP에 `lic`·`lic2`를 묶는 것으로 확장 가능
- 그때 바뀌는 것: 앱 DSN이 primary(VIP)를 가리킴, standby는 읽기 전용이라 로컬 DB 직접 쓰기 불가, `[ROLE]` 절체 시 전환
- 현 단계에서는 설계하지 않음 (사용자 결정)

### 8.5 클라이언트 측 영향 (무변경)
- 라이선스: `lic`(A) 실패 시 `lic2`(B) 폴백 — B에 `lic_access_list`가 있으므로 정상 `Run`
- UDP 알람·6770 뷰어: `lic2`(B)만 사용 — 현재와 동일. B 장애 시 알람 중단(현재와 같은 약점, 이중화에서 해소)

## 9. 확정된 빌드 환경 **[사용자 결정 2026-10-13]**
