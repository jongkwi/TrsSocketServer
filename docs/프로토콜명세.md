## 2. TCP 스트림 재조립 규칙 (6321·6770 공통)

구현: `ReadMsgProc :500-537`, `SearchSocketSTX_ETX :617-641`, `CutSocketSTX_ETX :644-672`

### 2.1 수신 절차
1. `Receive(Rdata, 500)` — **반환값 무시**, 이후 처리는 `strlen` 기준. 따라서 **`0x00` 바이트 이후는 잘린다.** `:508-510`
2. `len = strlen(m_Rdata) + strlen(Rdata)`
   - `len < 1000` → `temp = m_Rdata + Rdata` (잔여 버퍼 앞에 붙임)
   - `len >= 1000` → `temp = Rdata` (**기존 잔여분 폐기**) `:511-514`
3. 반복: `SearchSocketSTX_ETX(temp)` → `CutSocketSTX_ETX(temp)`; 반환 `len <= 0`이면 종료
4. 종료 시 `strlen(temp) < 500`이면 `m_Rdata = temp`, 아니면 `m_Rdata = ""` (폐기) `:523-526`

### 2.2 프레임 탐색 (`SearchSocketSTX_ETX`)
- 첫 STX를 찾은 뒤, 그 이후를 스캔하며 **STX가 다시 나오면 시작점을 갱신**, **첫 ETX에서 종료**. `:624-636`
- 즉 `STX a STX b ETX` → payload는 `b`. 앞의 `a`는 버려진다.
- 첫 STX 이전의 바이트는 무시된다 (ETX가 먼저 와도 무시).

### 2.3 프레임 절단 (`CutSocketSTX_ETX`)
| 상황 | 동작 |
|---|---|
| STX·ETX 모두 있음 | STX 다음 2바이트를 `atoi` → `ret` (**ServerProc에서 미사용**). STX~ETX 사이를 `ServerProc`로 전달. ETX 이후를 버퍼에 남김. 반환 `len = endPos-startPos+1` |
| STX만 있음 | STX부터 끝까지 보존 (다음 수신과 결합). 반환 0 |
| STX 없음 | 버퍼 전체 폐기. 반환 0 |

### 2.4 포팅 시 재현해야 할 경계 동작 **[확인]**
- 한 번의 수신에 여러 프레임이 있으면 순서대로 모두 처리된다.
- 프레임이 수신 경계에 걸치면 STX부터 보존되어 다음 수신과 결합된다 (단, 잔여+신규 ≥ 1000이면 잔여 폐기).
- payload 안에 `0x00`이 있으면 그 이후가 사라진다 (클라이언트는 NUL을 보내지 않는 것으로 보임 [추정]).

## 3. TCP 6321 — IPCS 라이선스 체크

구현: `ServerProc :702-729` (`case IPCS_PORT`)

### 3.1 요청 (클라이언트 → 서버)
```
STX  IVR 0xFF <MAC> IP: <ip>  ETX
      │    │    │        └── 클라이언트 자기 IP (szMyIP, 문자열)
      │    │    └── NIC MAC 주소 (ReadNicMac, 첫 번째 유효 NIC) → LOG_DATA 컬럼
      │    └── 필드 구분자 0xFF (서버는 index 3을 건너뜀)
      └── 3바이트 타입 문자열 "IVR" → LOG_TYPE 컬럼 (다른 제품은 다른 3글자일 수 있음 [추정])
```
클라이언트 측 구현 **[확인 — 사용자 제공 클라이언트 소스 `docs/reference/client_license_check.cpp` `WriteServerLog`]**
- 생성: `sprintf(buf, "%c%s%c%sIP:%s%c", 0x02, "IVR", 0xff, szMac, szMyIP, 0x03)`
- 접속 대상: `lic.onpia.co.kr:6321`, 실패 시 `lic2.onpia.co.kr:6321`. 둘 다 실패하면 프로세스 종료
- 접속 후 **1초 대기** 뒤 1프레임 송신, 1회 수신

서버 파싱 **[확인]** `:705-711`
- `nFindPos = Find("IP:")` — **`nFindPos > 3`일 때만 처리**. 아니면 로그만 남기고 **무응답**.
- `strType = Mid(0,3)`, `strMac = Mid(4, nFindPos-4)`, `strIP = Mid(nFindPos+3)`
- `strIP`가 비어 있지 않으면 `INSERT INTO IPCS_LOG (LOG_DATA, LOG_IP, LOG_TYPE, LOG_REAL_IP)` = (strMac, strIP, strType, **peer IP**) `:714-716`

### 3.2 판정과 응답 (서버 → 클라이언트) **[확인]** `:719-727`
```sql
select count(*) from lic_access_list where nasa_con_ip='<peer IP>' and nasa_use='Y'
```
| count | 응답 바이트 | 길이 |
|---|---|---|
| `<= 0` | `Close` | 5 |
| `>= 1` | `Run` | 3 |

- **응답에 STX/ETX·개행·NUL 없음. 원시 문자열 그대로.**
- 판정 기준은 payload의 IP가 아니라 **소켓 peer IP**다.
- 응답 후 서버는 연결을 끊지 않는다. 클라이언트가 끊을 때까지 유지.
- `ret`(STX 뒤 2바이트 atoi)과 첫 글자 `command`는 이 포트에서 사용하지 않는다.

### 3.3 예시
요청: `02 'I' 'V' 'R' FF '0' '0' '-' '1' '1' ... 'I' 'P' ':' '1' '9' '2' '.' '1' '6' '8' '.' '0' '.' '1' '0' 03`
응답: `'R' 'u' 'n'` 또는 `'C' 'l' 'o' 's' 'e'`

### 3.4 로그
`log\SOFT-YYYY-MM-DD.log`에 `IP:<peer>, Port:<peerport>, Data:<payload>` (`TcpLogging :704`)

### 3.5 클라이언트의 응답 처리 — 서버가 지켜야 할 제약 **[확인 — 클라이언트 소스]**
| 클라이언트 동작 | 서버 측 요구사항 |

## 4. TCP 6770 — 알람 클라이언트

구현: `ServerProc :731-742`, `AlarmUser_Send :1774-1820`

### 4.1 Heartbeat (클라이언트 → 서버 → 클라이언트) **[확인]**
- 수신 payload의 **첫 글자**가 `'3'`이면 (`atoi(1글자) == 3`) 응답. 그 외 payload는 **무시(무응답)**.
- 응답:
```
STX '4' 0xFF '' 0xFF HH:MM:SS ETX
02  34  FF      FF  "14:05:33" 03        (길이 13)
```
`sprintf("%c%d%c%s%c%s%c", 0x02, 4, 0xff, "", 0xff, szTime, 0x03)` `:738`

### 4.2 서버 푸시 (서버 → 모든 6770 클라이언트) **[확인]**
```
STX <cmd> 0xFF <message> 0xFF HH:MM:SS ETX
```
- `cmd`: `%d` 10진 문자열. `1` = 일반 알람(기본값 `TrsSocketServer.h:65`), `2` = 문자 일시정지 중 로그장애 알림(`TrsSocketServer.cpp:1209`)
- `message`: 최대 1000바이트로 절단 (`:1780-1782`), CP949
- 대상: `m_connectionAlarmList`의 모든 소켓에 순서대로 `Send`. 전송 결과는 `Alarm-YYYY-MM-DD.log`에 기록.
- 발생 시점: UDP 장애 이벤트 처리 후(`:1158`, `:1209`, `:1247`), 링크 단절 감지(`:1485`)

## 5. UDP 5363 — 장애 이벤트 수신

구현: `ReadUdpMsgProc :541-574`, `ServerUdpProc :783-1295`, `IVRSMSSendProc :1299-1348`

### 5.1 데이터그램 처리 **[확인]**
- `ReceiveFrom(500)` 1회 = 데이터그램 1개. 데이터그램 안에서 STX/ETX 탐색(2.2와 동일 규칙), **한 개 프레임만** 처리. STX 또는 ETX가 없으면 조용히 폐기.
- 응답(ACK)은 **송신자 IP:port로 `SendTo`**.

### 5.2 요청 프레임
```
STX <idx> 0xFF <nType> 0xFF <sysIP> 0xFF <msg> [0xFF <from> 0xFF <to>] ETX
```
| 인덱스 | 필드 | 설명 | 저장 버퍼 |
|---|---|---|---|
| 0 | idx | 정수 (atoi, 사용 안 함) | - |
| 1 | nType | 이벤트 유형 (5.4 표) | - |
| 2 | sysIP | 클라이언트가 보고하는 자기 IP (`szIP`) | `char[21]` — 20자 초과 시 오버플로 |
| 3 | msg | 메시지 (프로세스명, 디스크명, 퍼센트 등) | `char[1024]` |
| 4 | from | IVR(200/201) 전용: 발신번호 | `char[31]` |
| 5 | to | IVR 전용: 수신번호 | `char[31]` |

- `StrSplit :1708-1722`: 최대 50필드 × 1024바이트, 경계 검사 없음. 연속된 `0xFF`는 빈 필드를 만든다.
- `szRealIP` = 데이터그램 **송신자 IP** (peer). 표시용 `szUseIP` = `szRealIP`가 `sysIP`와 같으면 `szRealIP`, 다르면 `"szRealIP(sysIP)"` `:823-827`

### 5.3 ACK 규칙 **[확인]**
ACK 프레임 = `STX + <수신 payload 그대로> + ETX` (`:840`). **아래 경우에는 ACK를 보내지 않는다.**

| 무응답 경로 | 위치 |
|---|---|
| nType 200/201 (IVR) | `:832-835` |
| 수신자(SITE_SMS_USER)는 있으나 `CallCenter_Link`에 사이트가 없어 신규 등록한 경우 | `:856-888` |
| 사이트는 있으나 `cc_use != 'Y'` | `:890-897` |
| 사이트명 `'신규1'`이고 `cc_insert_time`으로부터 3시간 초과 | `:902-910` |
| **nType 100 (LINK_CHECK)** — 정상 경로지만 `SendTo` 호출이 없음 | `:1016-1033` |

그 외 모든 경로(알 수 없는 nType, 알 수 없는 IP, 수신자 없음 포함)는 ACK를 보낸다.

### 5.4 nType 전체 표 (`UdpSocket.h:12-44`)

| nType | 이름 | 알람 메시지(`{site}-{ip}에서 …`) | 알림톡 템플릿 | 긴급 | 이메일 이벤트 | ACK |
|---|---|---|---|---|---|---|

- 발생 위치 4곳: `:874`(tableCheck001), `:1191`(UDP 이벤트별 코드), `:1265`(newSite001), `:1510`(linkDataError001). 테스트 버튼에도 1곳(`Dlg.cpp:380`, procError001)
- **서버는 INSERT만 한다.** 카카오 API 호출, 발송 결과 조회, 상태 갱신, 템플릿 관리 코드는 없다. 실제 발송은 이 테이블을 읽는 외부 MTS 에이전트가 담당한다 **[추정]**. 서버에서 알림톡 연동 = ODBC INSERT 1문장.
- 실패 처리: `ExecSql`이 0이 아니면 `SqlErr-YYYY-MM-DD.log`에 SQL 전문 기록. 재시도 없음 (DirectODBC의 재접속 1회 제외)
- 고정 컬럼 값: `TRAN_CALLBACK='15889310'`, `TRAN_SUBJECT='OnpiaATalk'`, `TRAN_TYPE=5`, `TRAN_STATUS='1'`, `TRAN_REPLACE_TYPE='S'`, `TRAN_REPLACE_MSG=TRAN_MSG`(알림톡 실패 시 같은 본문으로 SMS 대체 발송용 **[추정]**). 의미는 MTS 에이전트 사양 확인 필요
- 템플릿 코드(`TRAN_TMPL_CD`) 30종: procError001/procReturn001, cpuError001/cpuReturn001, diskError001/diskReturn001, memError001/memReturn001, sockError001/sockReturn001, sockLinkError001, sockDisconError001, pingError001/pingReturn001, procLogError001, linkDataError001/linkDataReturn001, nasConError001/nasConError003/nasConReturn001, nasUploadError002/nasUploadReturn001, nasDiskError001, recDiskDel001, recDiskThres001, newSite001, tableCheck001, unknownCmd001/002/003.
